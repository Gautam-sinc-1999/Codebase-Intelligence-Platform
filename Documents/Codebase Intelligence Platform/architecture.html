System internals · reference

Codebase Intelligence

A conversational RAG system over source code. It parses a repository into symbols, embeds them, builds a call graph across the frontend/backend boundary, and answers questions with citations that point at real line ranges.

FastAPI + React8,259 lines backend2,447 lines frontend 520 tests · 2 graph backends

01What it actually does

Four question types, each answered from a different combination of evidence.

Feature explanation
"How does checkout work?"
Traces the flow across layers — component → endpoint → service → model.
Code location
"Where is the discount calculation?"
Exact file and line range, from the chunk index.
Dependency analysis
"What calls record_audit?"
Every call site, read from the graph — not from the snippets.
Change impact
"If I change this, what breaks?"
Confirmed callers, affected tests, files to review.

The distinction that matters in an interview: this is not "embed the files and hope". Retrieval returns the top k chunks by relevance. For a helper called from fifty places, that returns a handful of call sites and the model reports those as the complete set. The static analysis knows all fifty, and it is injected into the prompt as authoritative fact.

02Architecture

Six layers. The rule that keeps it tractable: each layer takes a plain data structure from the one below and knows nothing about how it was produced. That is why adding GitHub import required no change to parsing, embedding or answering — only a new way to obtain a directory.

Request block diagram

The same six layers, drawn as the path a request actually takes. Solid lines are the request; dashed lines are reads from a store.

Why four stores and not one

StoreHoldsWhy it can't be merged
MongoDBrepository records, conversations, messagesThe only durable, queryable, multi-instance store. Threads live here because they are the one thing that cannot be regenerated.
ChromaDB384-dim embeddings, one collection per repositorySemantic similarity needs a vector index; a document store cannot do nearest-neighbour.
Neo4jSymbol/File nodes, CALLS / ROUTES_TO / CONTAINS edgesMulti-hop traversal ("what transitively depends on X") is a graph query, not a join.
Diskchunk index + content-hash manifestThe source of truth for citations, and what makes incremental re-index possible.

03The indexing pipeline

A zip or a clone arrives as a directory. Six stages turn it into something answerable. The function at the centre — index_repository_folder(dir, repo_id, name, force_full) — takes a plain path and has no idea whether it came from an upload or a git clone.

01

Discovery

Walks the tree and decides what is worth reading. Streamed, so only the file being parsed is in memory.

  • Encoding detection — BOM first, then a PEP 263 coding: declaration, then strict UTF-8, then cp1252/latin-1. A guess is flagged as a guess.
  • Binary check — null bytes, but a BOM overrides: UTF-16 text is full of nulls and was being discarded as binary.
  • Secret filter — .env, *.pem, id_rsa, credentials.json are never written to disk, let alone indexed.
  • SHA-256 per file — the basis of incremental re-index.
app/ingestion/discovery.py · 270 lines
02

Parsing

Two parsers, chosen by language. Both emit the same CodeEntity shape, so everything downstream is language-agnostic.

  • Python — the stdlib ast module. Recursive scope walking, so nested classes and closures are indexed, not just module-level definitions.
  • JS / TS / JSX / TSX / Java — tree-sitter. Real syntax trees mean line ranges are actual definition extents rather than regex approximations.
  • Route detection — FastAPI @router.post("/x"), Flask @app.route(..., methods=[...]) (defaulting to GET), Blueprint and APIRouter prefixes. Produces "POST /api/checkout".
  • Call extraction — what each symbol calls, and what HTTP requests it issues.
app/ingestion/ast_parser.py · 446 · treesitter_parser.py · 458
03

Chunking

One chunk per symbol — a function, method, class or endpoint — carrying its code, its line range and a generated summary line used for embedding.

# the identity of a chunk
chunk_id = md5(f"{repo_id}:{file_path}:{symbol}:{start_line}")

Symbol-level rather than fixed-window is the decision worth defending: a 512-token window splits functions in half and cites line ranges that mean nothing. A chunk here is a thing a developer would point at.

app/ingestion/chunker.py · 58 lines
04

Embedding

all-MiniLM-L6-v2 via ONNX, 384 dimensions, one Chroma collection per repository (repo_<id>). This stage is ~89% of indexing time, which drives almost every performance decision in the system.

Only changed chunks are re-embedded — unless a count check shows the collection and the index have diverged, in which case everything is re-embedded rather than leaving semantic search querying a near-empty collection while the index looks complete.

05

Graph construction

Call targets are resolved to real symbols, HTTP calls are matched to route handlers, and the result is written as nodes and edges. Covered in detail in §04.

06

Persistence

Chunks to data/indexes/<repo>.json, file hashes to <repo>.manifest.json, BM25 cache invalidated, status set to ready.

The manifest is what makes a re-index cheap: files whose hash is unchanged keep their existing chunks, so a sync after a one-file commit re-parses one file.

Interview point — incremental re-index

A fresh git clone shares no paths or timestamps with the previous one. Reuse works anyway because the manifest compares content hashes. Measured: changing 1 of 3 files re-parsed exactly 1 and reused 2.

Known limitation

start_line is part of chunk_id, so adding a comment at the top of a file changes the id of every symbol below it and forces a re-embed. Content-addressed chunks (hash(symbol + code)) would fix this and let branches share embeddings — the deferred phase-3 design.

04The call graph

This is what separates the product from pasting files into a chat window, so it is worth being precise about.

Node identity

// a node is (repository, file, symbol) — all three
MERGE (s:Symbol {name: chunk.symbol, file_path: chunk.file_path, repo_id: $repo_id})

Keying on the symbol alone merged a/util.py:helper and b/util.py:helper into one node — they shared callers, a file path and a line range, and the last one indexed silently overwrote the other. Same-named helpers are ordinary code structure, not an edge case.

Three edge types

EdgeMeaningCounts as a caller?
CONTAINSFile → SymbolNo — a file does not call a function
CALLSSymbol → Symbol, in-processYes
ROUTES_TOComponent → endpoint handler, across HTTPYes — invocation over the network is still invocation

The cross-stack chain

The piece interviewers tend to find most interesting: a frontend fetch() is matched to a backend route by method and path — including path parameters — so dependency analysis crosses the HTTP boundary.

Multi-method routes

@app.route("/items", methods=["GET","POST"]) becomes the single route string "DELETE|GET|POST /items" and the handler is indexed under each verb. One handler stays one node — emitting one entity per method would split the call graph across nodes covering identical lines.

05Retrieval

Three signals are fused, then a code-aware reranker decides which candidate is the best answer rather than merely the most relevant.

Stage 1 — fusion

SignalWeightCatches
Vector similarity (Chroma)+2.5Paraphrase — "how do we bill people" finds charge_card
BM25 keyword× 0.1Exact terms, rare identifiers
Exact symbol match+3.0The user naming a function outright
Symbol tail match+2.0calculate_discount → DiscountService.calculate_discount
File path match+1.5"in decide.py"

Semantic search alone fails on rare identifiers; keyword search alone fails on paraphrase. The weights encode that an exact symbol name is stronger evidence than semantic proximity.

Stage 2 — code-aware reranking

Fusion says how many signals found a candidate. The reranker applies signals only meaningful for code: query-term overlap with the symbol name, coverage, entity type, and penalties — test files and very large chunks score lower, because "where is X defined" should not return the test that exercises it.

Subject resolution

Separate from retrieval, and a genuinely subtle part. Retrieval rank answers what is relevant, not what did you name:

  1. A symbol the user named explicitly (backticks outrank bare words)
  2. A file or module they named — decide.py, "the decide module"
  3. The conversation's current subject, when the query refers back ("who calls it?")
  4. Only then, the top-ranked hit

Without step 2, "if I change the decide module, what breaks?" matched nothing, fell through to rank, and produced an impact report about a helper in a test file.

06Answering

Intent classification

Whole-word token-sequence matching with scoring — not substring containment. The old version matched "change" inside "unchanged":

"Which parts are unchanged?"          → CHANGE_IMPACT      ('unchanged' ⊃ 'change')
"Is the parser independent of X?"     → DEPENDENCY_ANALYSIS ('independent' ⊃ 'depend')
"Describe the workflow engine"        → FEATURE_EXPLANATION ('workflow' ⊃ 'flow')

Each intent is scored and the best wins; a two-word phrase scores its own length, so "who calls" outranks a lone "flow". Measured on a 18-question set: 10/18 → 18/18.

Static analysis facts in the prompt

The single most important design decision. The graph was being built, queried and rendered — and the answer generated from snippets alone, so the panel and the prose could disagree inside one response.

STATIC ANALYSIS FACTS (authoritative — from the parsed call graph, not the snippets):

CALLERS OF `record_audit` (13 total) — this list is complete; do not describe
it as partial or as examples:
  - `handle_request` in api/handlers.py:3
  - `operation_1` in services/module_1.py:3
  ...

These facts were computed by walking the syntax trees and call graph. Where a
snippet below appears to disagree, the facts above are correct — the snippets
are an excerpt, not the whole repository.

Placed before the code, because the snippet block can be long and anything after it competes for attention. Measured on a helper called from 13 files where retrieval surfaced 5: the answer went from naming 5 of 13 — presented as complete — to 13 of 13, with the correct count in the prose.

Prompt budgeting

A prompt that consumes the whole per-minute token budget does not fail outright — it succeeds once and rate-limits everything for the next minute. The budget is allocated, not assumed:

SectionShareRationale
System promptfixedCounted against the budget, not ignored
Static analysis facts25%Authoritative but compact; capped in aggregate across all blocks
History15%Only resolves references; oldest turns dropped first
Retrieved coderemainderWhat stops the model inventing behaviour — so it gets what is left

Worst case measured: 7,255 → 3,006 tokens against an 8,000 TPM limit.

Honest degradation

When no model is reachable, a rule-based template answers from the retrieved chunks. It cites real files and line ranges — it is simply not equivalent. The response carries degraded: true and the UI says so, rather than presenting a visibly poorer answer with no explanation.

What goes into the model

Two messages: a system prompt that never varies, and a user turn assembled per query. Here is the real thing, trimmed only where marked.

Message 1 — system prompt (1,739 chars, constant)

You are a helpful, senior software engineer pair-programming with a developer
onboarding to a codebase.

GROUNDING RULES (these override style):
A.  Answer ONLY from the material in the user turn: the Static Analysis Facts
    and the Retrieved Code Context.
A1. The Static Analysis Facts are AUTHORITATIVE and COMPLETE for what they
    state. The snippets are the top matches for this question, not the whole
    repository, so they will often show fewer call sites than the facts list.
    When the two appear to disagree, follow the facts. Never describe a list
    given in the facts as partial, as 'examples', or as 'a handful' — report it
    as the complete set it is, and give the count.
B.  Never invent file paths, symbol names, line numbers, or behaviour that is
    not visible in that context.
C.  When you cite a location, use the exact path and line range shown.

STYLE: conversational first · 2-4 sentence summary · name key files naturally
· offer two follow-ups · answer follow-ups directly.

Rule A1 is the whole product in one paragraph. Without it the model averages two sources that disagree — and the snippets, being longer and more concrete, tend to win.

```python
def calculate_discount(self, user_id: str, subtotal: float,
                       coupon_code: Optional[str] = None) -> float:
    """Calculates total discount for an order."""
    if subtotal <= 0:
        return 0.0
    discount = 0.0
    if coupon_code and coupon_code.upper() in self.COUPON_DATABASE:
        discount = subtotal * self.COUPON_DATABASE[coupon_code.upper()]
    if subtotal >= 100.0 and not coupon_code:
        discount = max(discount, subtotal * 0.05)
    return round(discount, 2)
```

Order is deliberate

Facts come before the code. The snippet block runs to several thousand characters, and anything placed after it competes for attention with a wall of source. The header line above each snippet is what rule C tells the model to cite from — which is how citations end up pointing at real line ranges.

What comes back

The model returns prose. The endpoint returns a structured payload of which prose is one field — the rest is computed, not generated, so the UI can render panels the model cannot fabricate.

| Caller                     | File                                  | Location |

08Storage & conversation memory

What lives where

MongoDB
  repositories           repository_id, name, source, branch, commit_sha, languages
  conversations          one doc per thread — title, summary, working_context, counters
  conversation_messages  one doc per message, ordered by an explicit `seq`

ChromaDB   repo_<id>               384-d vectors
Neo4j      Symbol / File nodes     CALLS · ROUTES_TO · CONTAINS
Disk       data/indexes/<id>.json  chunks + code · .manifest.json = file hashes

Why two collections, not one document

A thread has no natural size ceiling. One document with an embedded message array would approach Mongo's 16 MB limit and force every read to pull the entire history when the UI wants the last twenty turns. Splitting them keeps read_messages(limit=20) cheap.

seq rather than a timestamp, because two turns saved in the same millisecond must still come back in order.

Write-through, not write-behind

Conversations are written to Mongo synchronously on every turn. The alternative — buffering in Redis and checkpointing — was measured and rejected:

Mongo insert
0.155 ms
Redis RPUSH
0.087 ms
One LLM turn
2,000–8,000 ms
Write as share of a turn
0.005%

There is no bottleneck to buffer, and a checkpoint window would put the only non-regenerable data in the system behind a lossy cache to save 0.068 ms. Indexes, embeddings and graphs all rebuild from source in seconds; a conversation exists nowhere else.

Citations are pointers, not payloads

A stored turn keeps (file_path, symbol, start_line, end_line) — not the code. One measured message held 306 KB of inlined source, 98% of the stored turn, of which the UI rendered about 1 KB.

The other half of that trade is GET /repositories/{id}/snippet, which resolves a pointer back to source when the reader expands a citation. Without it the code viewer worked during a live session and silently went inert after a reload.

09GitHub import & drift

The whole feature rests on one observation: the zip path is extract → directory → index; git is clone → directory → index. Only acquisition changes.

Derived identity

repository_id = "gh_" + sha256("github.com/owner/repo@branch")[:12]

Stable across syncs, distinct per branch, case-insensitive like GitHub itself. A zip upload mints a fresh uuid, so uploading twice makes two unrelated repositories — wrong for something with an upstream.

A URL is hostile input

A clone is remote-controlled disk writing. Validation is a pure function, tested directly:

RejectedBecause
file:///etc/passwdA perfectly valid clone URL that reads local disk
https://github.com@evil.com/a/bUserinfo — the real host is evil.com
https://user:token@github.com/…Credentials leak into ps and logs
github.com.evil.comSuffix impersonation
--upload-pack=touch /tmp/xReads as a git option, not a URL

Defence in depth: -- before every argument so nothing can be read as a flag, GIT_TERMINAL_PROMPT=0 so a private repo fails fast instead of blocking on a credential prompt, and GIT_ALLOW_PROTOCOL=https so git itself refuses anything else.

Drift detection — three states, not two

A thread is a conversation about a specific version of the code. The obvious comparison is index vs remote, but a third case appears the moment one repository has two threads:

StateMeansOffers a sync?
currentNothing changed—
behindUpstream movedYes
thread_behindAnother thread already synced this repoNo — there is nothing to pull

Aged citations

After a sync, an old pointer still resolves — against different code. A citation recorded as checkout.py:40-58 may now be a different function, and the viewer would show it with complete confidence.

Pinning each thread to its own index would be exact and unaffordable: indexing every commit of a 500-commit repository is roughly 428,500 chunks and ~16 GB. So the answer is label, do not pin — each turn records the SHA it was answered at, and /snippet?at_sha= returns stale: true when they differ.

10Async work & failure handling

Why shutdown waits instead of cancelling

The subtlest bug in the system, and a good interview answer.

run_in_executor hands work to an OS thread. Cancelling the awaitable returns immediately while the thread keeps running — it is not interruptible. A shutdown that cancels therefore reports a clean stop while a live thread is still writing embeddings to ChromaDB and nodes to Neo4j. Closing the vector store at that point tears the client out from under a live upsert.

# drain() waits. It does not cancel.
done, still_running = await asyncio.wait(pending, timeout=timeout)
self._executor.shutdown(wait=True)   # the guarantee

The test asserts not that drain() returned, but that the worker thread's final statement ran before it did.

Where the async boundary falls on upload

The uploaded stream exists only for the duration of the request, so saving and extracting the archive happens inline; indexing is the slow half and becomes the job. A corrupt or hostile archive therefore still fails synchronously with a 400 — the right answer for a request that was never going to work — while a valid one returns 202 in 0.07 s.

Failure cleanup

Indexing writes embeddings before it builds the graph, so a failure in between stranded a populated Chroma collection owned by a repository Mongo never recorded — invisible and unreachable. Every failure path now purges all six places a repository lives.

Deliberate asymmetry

A failed import deletes its record: a row that cannot answer anything is worse than no row. A failed sync keeps it: the repository already worked and its previous index is still answerable, so a network hiccup should not destroy it.

12Defending the design

The questions most likely to be asked, and the honest answer to each.

"Why not just embed the files?"

Retrieval returns top-k. For a widely-used helper it returns a handful of call sites and the model reports those as complete. Measured: the graph knew 13 callers, retrieval surfaced 5, and the answer said "In the current codebase the callers are:" — then listed five. Static analysis is what makes a dependency answer correct rather than plausible.

"Why symbol-level chunks instead of a token window?"

Because citations have to be actionable. A fixed window splits a function in half and cites a line range that corresponds to nothing. A symbol is a thing a developer can open.

"How do you know it works on a repository you didn't write?"

Verified against psf/requests — 865 chunks, 947 nodes — with answers citing sessions.py, Session.prepare_request and SessionRedirectMixin. Two branches of the same repo were indexed side by side and confirmed isolated: 0 shared chunk ids, 0 graph edges crossing repositories.

"What's the weakest part?"

Worth having a real answer ready:

  • Chunk ids include start_line, so a comment at the top of a file invalidates every symbol below it. Content-addressed chunks would fix it and let branches share embeddings.
  • Every branch is a full index — ~857 chunks and ~32 MB per branch, with no sharing between branches that are 99% identical.
  • Call resolution is name-based, not type-aware. Dynamic dispatch and runtime-constructed calls are invisible.
  • The graph view caps at 200 nodes. It now says so and keeps the most connected ones, but it is still a slice.

"How is it tested?"

520 tests, run against both graph backends — Neo4j and the in-memory NetworkX fallback. That is not redundancy: running both is what catches the two backends quietly disagreeing, which happened three times (label casing, whether the queried symbol appears in its own dependencies, and whether max_depth was honoured at all).

Fixes are mutation-checked — the guard is removed and the suite re-run to confirm a test actually fails. Several tests that looked fine were passing by luck, and one such check exposed real non-determinism: candidate paths iterated out of a set, so equal-scoring files were separated by hash order, which varies between processes.

Every figure on this page was measured on the running system.
